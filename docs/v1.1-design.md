# knowledge-sdk v1.1.0: permission-aware spaces, answers and consumption

## 1. Boundaries and compatibility

The SDK owns spaces, authoritative ACL decisions, versioned evidence, retrieval,
answer orchestration and consumption contracts. Hosts own authentication, directory
state, user interfaces, business workflows and any external model implementation.
There is no Flask/StratAI import, directory database dependency, model provider
selection or automatic generation. Core `dependencies = []`; only the optional
HTTP server imports FastAPI. HTTP client, SQLite, contracts and extractive answers
use the standard library. Existing optional embedding adapters are unchanged.

All v1.0 positional arguments remain valid; `create_kb` adds keyword-only options.
All new dataclass fields have defaults. Existing 108 tests are unchanged. New
exports are additive; package and health version are 1.1.0. SQLite remains schema
version 1: `CREATE TABLE IF NOT EXISTS consumer_bindings` is additive, and JSON
rows decode missing fields using defaults. No destructive migration is needed.
Older v1.0 binaries are not promised to decode newly written v1.1 JSON models;
back up databases before downgrading binaries.

### Explicit security upgrade vs legacy behavior

v1.0 allowed any authenticated user to create an enterprise KB and allowed space
owners/editors to write. Enforcing the new administrator-only rule retroactively
would break the v1.0 API's behavior. Therefore:

* Omitted `space_type` maps visibility to the standard tier **and preserves v1.0
  membership behavior** (`legacy_permissions=True`), including existing DB rows.
* Explicit `space_type` creates a strict v1.1 space (`legacy_permissions=False`).
  This marker is persisted, so loading a KB cannot accidentally re-enable owner
  privileges. The public creation API does not accept this marker from callers.
* New four-level document ACLs apply strictly in **both** kinds of spaces, without
  owner/admin bypass. Omitted `access_level` preserves old allow-list semantics.

Hosts that need the new tier policy must explicitly provision strict spaces;
visibility inference alone is not an implicit access-policy migration. A host
can migrate old spaces after separately auditing their memberships/ownership.
This release performs no deployment, data migration or host repository changes.

## 2. Space tiering and management

`SpaceType` is a string enum: `enterprise_public`, `department`, `personal`.
`KnowledgeBase` adds `space_type`, `owner_department_id`, `owner_user_id`.
Strict spaces canonicalize visibility to enterprise/team/private, respectively.
Legacy mapping is enterprise → enterprise_public, team → department, private →
personal. Personal owner defaults to the existing `owner_id`.

| Strict tier | Upload/manage | Baseline read boundary |
|---|---|---|
| enterprise_public | `org_roles` contains `admin`, or trusted `public_kb_admin=True` | same organization |
| department | `owner_department_id` appears in trusted `managed_department_ids` | same department, descendant department, departmental manager, or explicit KB membership |
| personal | `actor.user_id == owner_user_id` | owner or explicitly granted KB membership |

The document ACL can narrow, never widen, the KB read boundary. Explicit KB
membership is a sharing/read capability, not a way to escalate strict-tier write
privileges. A strict enterprise space's original creator loses write access when
its organization-admin claim is revoked. An organization admin is not implicitly
a department manager or the owner of another person's personal space.

`can_manage_kb(actor, kb, member_role=None)` and `can_upload_to_kb(...)` are pure
helpers, also exposed as client methods taking `kb_id`. In legacy spaces these
retain owner/admin and editor semantics. Strict department creation requires a
nonempty owner department; other-person personal creation is denied.

## 3. Trusted Actor and directory adapter

Actor keeps the original user/org/space-role/department fields and adds:

* `ancestor_department_ids=()` — ancestors only, supplied by host.
* `org_roles=()` — raw organization roles, never inferred from space `roles`.
* `clearance_level=""`, `clearance_tags=()`.
* `managed_department_ids=()` and `public_kb_admin=False` — explicit management
  claims; ordinary membership and role labels do not imply managerial authority.

Sequence claims are validated and normalized to immutable tuples. The host must
construct them from a current authenticated directory snapshot, never request
headers supplied by end users. In particular `approver → space admin` in an old
host adapter does **not** confer enterprise-public administration in v1.1.

### Department forest algorithm

`expand_department_ancestors(department_ids, departments)` accepts flat dictionaries
with `id`, `parentId` (or `parent_id`), optional organization identity. It validates
the complete supplied forest, rejecting duplicates, missing parents, self-cycles,
longer cycles, malformed identifiers and explicitly cross-organization edges.
Unknown user departments are rejected. It follows parent links with a local
visited set and memoized ancestor chains, then returns a sorted deduplicated union.
Traversal is iterative, not limited by Python recursion depth. Work/memory scale
with nodes plus materialized ancestor-chain lengths (worst-case quadratic for a
single deep chain); no graph/database dependency is used.

For `root → parent → child`, user `department_ids=('child',)` gets
`ancestor_department_ids=('parent', 'root')`. Multiple direct departments union
their ancestors. The helper does not manufacture direct memberships. Hosts must
supply a tenant-filtered forest and re-evaluate claims after organizational moves.

## 4. Four-level ACL matrix

All content reads first check same org, archive status, explicit legacy denials,
and KB access. **Denials override everything.** Once `access_level` is nonempty,
its policy is mandatory even for the document owner and enterprise administrator.

| access_level | Positive condition after hard boundaries |
|---|---|
| org_public | any actor passing KB/org boundary |
| department | `allowed_department_ids` intersects direct `department_ids`; if `include_sub_departments=True`, additionally match `ancestor_department_ids` |
| role_clearance | each configured dimension must match: any `allowed_org_roles`, sufficient `required_clearance`, any `allowed_clearance_tags` |
| personal_only | document owner, or explicit `allowed_user_ids` |

Empty department grants and empty role/clearance policy deny everyone. Inside a
role or tag list, entries are alternatives; **between** roles, clearance and tags,
conditions are AND. Standard clearance order is public < internal < confidential
< restricted. A custom `required_clearance` uses exact label equality; unknown
levels never get implicitly promoted. Tags are a separate intersection condition.
The personal owner is the document's immutable owner, not the containing KB owner.
Legacy `deny_roles` examines the original space `roles`, not `org_roles`.

Without `access_level`, old owner/admin and allow_users/roles/departments behavior
is preserved. Existing deny rules continue to override new public grants. ACL
set operations require space-management rights; the policy can intentionally
prevent its administrator from reading document text without preventing ACL repair.

### Fail-closed authority

Keyword/vector/hybrid candidates are only identities. Every hit is reloaded from
SQLite and checked for current version, valid chunk, organization, KB membership,
archive status and document ACL. Vector payload text or claimed ACL never becomes
evidence. Missing, stale, foreign and unauthorized candidates are discarded.
Scope filters run before final top-k selection. `retrieve`, `reference`/`create_ref`,
`attach`, `verify_ref` and receipt consumption use the same `_read` policy. Permission
revocation thus affects existing references too; a hash alone is never a grant.

## 5. ask(): explicit generation only

```
ask(actor, question, scope=None, top_k=5, mode='keyword', generator=None,
    excerpt_policy=None, min_score=0.0, binding=None) -> KnowledgeAnswer
```

`AnswerGenerator.generate(question, evidence_hits, scope, actor) -> GeneratedAnswer`
is a structural Protocol. The built-in `ExtractiveAnswerGenerator` simply emits
numbered, verbatim excerpts; it makes no network calls and reports
`model_called=False`. A host plugin explicitly reports whether it called a model
through `GeneratedAnswer.model_called`. Generator invocation and external model
invocation are distinct: a successful extractive answer invokes the former only.

Flow:

1. Validate question, mode, top-k, finite nonnegative threshold and scope structure.
2. Retrieve authorized candidates in scope. With a binding, intersect its default
   scope **before** final top-k. Default keyword mode works without optional
   embeddings; select `hybrid` explicitly when an index/embedder is configured.
3. Discard empty excerpts and scores below `min_score`. Current scores are weighted
   reciprocal-rank-fusion values, **not confidence probabilities**; hosts must
   calibrate thresholds to their retrieval configuration. The default accepts
   any nonempty authoritative hit, not a claim of semantic correctness.
4. If none remain, return `status='refused'`, a nonempty `refusal_reason`, empty
   answer/citations/receipts/evidence and `model_called=False`. **Never call the
   generator.** Explicit unauthorized document selectors also yield this uniform
   refusal, rather than becoming an existence oracle. `validate_scope` remains
   available when a host explicitly wants permission-validation errors.
5. Build and verify versioned refs and consumption receipts **before generation**.
6. Call the selected generator exactly once with authorized evidence only.
7. Reject invalid generator results. Recheck evidence permissions after generation
   (including re-entrant local revocation). If access changed, withhold all answer
   text/evidence and refuse; preserve truthful `model_called` reporting.
8. Return answered text, citations, receipts, evidence_hits, model_called and
   scope_applied and binding_applied. `scope_applied` records the caller/default scope; when both caller
   and binding are supplied, the binding is an additional intersection constraint,
   `binding_applied` records it explicitly, and successful receipts record its consumer identity/stage.

`ingest`, list, search, retrieve, attach and binding operations never call an answer
generator. Explicit vector search may still invoke a configured **embedder**; the
zero-generation contract does not conceal that distinct retrieval dependency.
A supplied generator is trusted code: the SDK cannot prove that free-form output
is entailed, stop its own network use or infer whether it lied about model usage.
It cannot add unauthorized citations to the SDK's evidence list, however. For
strict offline provenance use the extractive generator; hosts remain responsible
for generative quality and additional calibrated semantic-quality rejection.
Generator failures propagate; there is no hidden retry, fallback model or spend.

## 6. Scope, bindings, references and receipts

`KnowledgeScope(mode='all_authorized')` selects all currently authorized content.
`mode='spaces'` requires `kb_ids` and/or `space_types` (both set means intersection).
`mode='documents'` requires `doc_ids`. Mixed/inconsistent or empty scoped selectors
are rejected rather than accidentally interpreted as an unrestricted search.
Scopes never grant read access. `validate_scope` checks named KB/doc identities;
type-only spaces are dynamic filters, not assertions that every such space is
accessible. ACL revocation is checked on every actual read regardless of prior
validation.

`ConsumerBinding(consumer_type, consumer_id, default_scope=KnowledgeScope(), stage='')`
represents a cycle, agent or other host consumer. Both contracts provide
`to_dict(camel_case=False)` and `from_dict()` with snake_case/camelCase keys, nested
scope conversion and JSON-safe sequences. Tagged encode/decode supports all new
response models without pickle or arbitrary type instantiation.

`bind_consumer` persists a validated default; `get_consumer_binding` revalidates it.
Storage keys include **organization AND user**, plus consumer type/id. This is a
private SDK preference, not proof of host-business ownership. Hosts authorize
business objects themselves. Passing a binding directly is also supported.
There is no cross-tenant global consumer lookup.

`create_ref` is the standard alias of `reference`; `attach(actor, ref, binding=None)`
returns `Attachment(reference, receipt)`. It rejects denied/unavailable refs,
forged excerpts and refs outside a binding's default scope. `verify_ref` returns
the same MaterialReceipt contract as consume: consumed/partial/denied/unavailable.
`partial` is a successful selected-material receipt, **not a failed consumption**.

Refs bind organization/document/version in `source_uri`, chunk IDs, exact excerpt
and SHA256 `excerpt_hash`. Consumption validates these against SQLite version and
chunk contents. Old versions remain referenceable after new uploads; archived
sources are unavailable. Receipt adds optional consumer_type, consumer_id and
used_by_stage. `verify_receipt(actor, ref, receipt, binding=None)` reconsumes and
compares the full evidence/status chain; when binding is supplied it also checks
consumer/stage and scope. Provenance labels are **not cryptographic attestations**;
a binding or host audit log is necessary to establish business consumption.
No action mutates a host cycle or agent automatically.

## 7. HTTP transport and authentication

All v1.0 endpoints remain. New POST endpoints share the existing tagged-JSON
`{"params": ...}` envelope and HMAC-authenticated Actor transport:

| Path | Operation |
|---|---|
| /v1/ask | ask |
| /v1/kbs/can-manage | can_manage_kb |
| /v1/kbs/can-upload | can_upload_to_kb |
| /v1/scopes/validate | validate_scope |
| /v1/bindings/validate | validate_binding |
| /v1/bindings | bind_consumer |
| /v1/bindings/get | get_consumer_binding |
| /v1/references/create | create_ref |
| /v1/references/attach | attach |
| /v1/references/verify | verify_ref |
| /v1/receipts/verify | verify_receipt |

`HttpKnowledgeClient` mirrors Local method signatures. Python generator objects
cannot be serialized or selected by remote callers: non-None remote generator
arguments are rejected locally, and any raw request `generator` key is rejected
server-side. Configure `create_app(..., answer_generator=plugin)` in trusted server
code. Default server behavior is extractive. Signature claims now include all
Actor fields; old payloads remain valid with defaults. Unknown claims are rejected.
HMAC covers exact method/path/query/body/Actor/time/nonce, preserving replay defense.
Never expose the signing secret to an untrusted browser. Development unsigned mode
remains explicitly opt-in; no new role headers are trusted.

## 8. Verification and acceptance

Run from repository root:

```
PYTHONPATH=src .venv-http/bin/python -m pytest -q
PYTHONPATH=src python3 -S -m unittest discover -s tests -t . -q
```

The second command disables all site packages, exercising standard-library-only
core behavior and skipping optional HTTP/live-backend tests. New tests cover tier
write boundaries, legacy inference, raw role separation, clearance/tags, direct vs
ancestor matching, malformed forests, fail-closed vector candidates, scope/binding
JSON and persistence, revoked permissions, versioned references, receipt tampering,
no-hit/low-score zero-generator refusal, re-entrant revocation, and authenticated
HTTP round trips/server-only generator configuration. Exact counts and worktree
inventory are recorded in `docs/v1.1-validation.md` after the final run.
